# Release Quality Audit

## هدف

پیش از commit/انتشار، یک تصویر صادقانه از وضعیت واقعی بده: چه چیزی اجرا شد، چه چیزی سبز است، چه چیزی مسدود است و چه ادعایی اثبات نشده. این مهارت انتشار را «تأیید» نمی‌کند؛ فقط شرایط را می‌سنجد و تصمیم انتشار را به انسان می‌سپارد.

## قواعد

- گیت فقط وقتی سبز است که کد خروج صفر باشد.
- پیام میانی یا باز شدن سرور یا اتمام یک مرحله، جای نتیجهٔ نهایی را نمی‌گیرد.
- آزمون اجرا‌نشده را موفق اعلام نکن.
- خطا/هشدار را برای سبز شدن پنهان نکن.
- نتیجهٔ CI محلی را با GitHub Actions یکی ندان، مگر هر دو اجرا و دیده شده باشند.
- سال بدون سند یا با داده مشکوک نباید فقط به دلیل عبور ساختاری منتشر شود.
- گزارش‌های ثابت باید از همان اجرا/داده باشند؛ گزارش قدیمی مدرک وضعیت جاری نیست.
- هیچ کلید خصوصی، رمز، توکن یا فایل خارج از خروجی عمومی را commit/آپلود نکن.
- انتشار Production بدون اجازهٔ صریح کاربر انجام نمی‌شود.
- اگر بخشی از گیت به دلیل محیط اجرا نشد، آن را `INCOMPLETE` گزارش کن.

## پیش‌نیازها

- working tree بررسی‌شده و تغییرات نامرتبط مشخص
- `requirements.txt` و وابستگی‌های OCR نصب‌شده
- دسترسی به PDFهای واقعی یا آگاهی از LFS pointer
- CI workflow: `.github/workflows/gate.yml`

## گردش کار

1. `AGENTS.md`، `docs/audit.md` و `README.md` را بخوان.
2. وضعیت مخزن را ثبت کن:

   ```bash
   git status --short
   git diff --stat
   ```

3. گیت رسمی را اجرا کن و exit code را نگه دار؛ خروجی را به `tail` محدود نکن مگر خروجی کامل در فایل ذخیره شده باشد:

   ```bash
   py -3 scripts/verify_all.py
   ```

4. در صورت شکست، اولین خطای واقعی را پیدا کن. تست را حذف/ضعیف نکن و اعتبارسنجی را غیرفعال نکن.
5. گزارش‌های کلیدی را بخوان و با داده جاری تطبیق بده:
   - `reports/history-audit.md`
   - `reports/identity-review-audit.md`
   - `reports/statistics-audit.md`
   - `reports/web-consistency.md`
   - `reports/year-coverage.md`
   - `reports/ocr-status.md`
   - `reports/audit/data-manifest.json`
6. تطبیق‌ها را جدا گزارش کن: ساختار داده، تاریخ، شاهد، تأیید، آمار، وب/JSON، OCR و پوشش سال.
7. سال‌های مسدود را صریح نگه دار؛ عدد کل سال‌ها را جای «سال منتشرشده» نگذار.
8. تفکیک کن:
   - تست‌های اجراشده و نتیجه
   - بررسی‌های اجرانشده
   - محدودیت محیط (LFS، OCR، شبکه، CI)
9. اگر گیت سبز است، تغییرات مرتبط را stage کن؛ فایل نامرتبط، log محلی، کلید و node_modules را وارد commit نکن.
10. commit فقط با پیام روشن و انگلیسی؛ push/deploy فقط با مجوز کاربر.
11. پس از push، اجرای GitHub Actions را بررسی کن. اگر مشاهده نشد، بگو «اجرا مشاهده نشد»، نه «CI سبز است».
12. وضعیت نهایی را یکی از `COMPLETED`، `PARTIALLY_COMPLETED`، `BLOCKED` یا `REQUIRES_HUMAN_REVIEW` اعلام کن.

## چک‌لیست انتشار

- [ ] `GATE_EXIT=0`
- [ ] تعداد تست‌ها و نتیجه ثبت شده
- [ ] هیچ تست حذف/ضعیف‌نشده
- [ ] manifest با داده جاری هم‌خوان
- [ ] آمار و وب/JSON بدون مغایرت
- [ ] ممیزی هویت بدون خطا
- [ ] دفتر تأیید بدون خطای زنجیره/امضا
- [ ] سال‌های مسدود مشخص و منتشرنشده
- [ ] OCR اجراشده و محدودیت آن ثبت
- [ ] هیچ secret/کلید خصوصی در stage نیست
- [ ] گزارش‌ها از اجرای جاری هستند
- [ ] CI واقعی دیده شده یا صریحاً «مشاهده نشد»
- [ ] مجوز انتشار Production گرفته شده

## خروجی

گزارش باید شامل این موارد باشد:

- commit/ref و زمان
- دستورهای اجراشده و exit code
- تعداد تست و شکست‌ها
- مراحل سبز/قرمز/اجرانشده
- گزارش‌های بازتولیدشده
- سال‌های مسدود و دلیل
- محدودیت‌های محیط
- وضعیت نهایی و اقدام بعدی

## آزمون‌ها و شواهد

- اجرای کامل `verify_all.py` و ثبت `GATE_EXIT`
- بررسی `git diff --cached --check`
- بررسی نبود secret در stage
- بررسی وجود و اعتبار YAML در `.github/workflows/gate.yml`
- بررسی هم‌خوانی گزارش‌ها با داده
- بررسی خروجی CI در GitHub در صورت دسترسی

## معیار پذیرش

- هیچ ادعای سبزی بدون اجرای واقعی نباشد.
- خطاها و مراحل اجرانشده آشکار باشند.
- تغییرات فقط مرتبط با وظیفه باشند.
- انتشار فقط با شرایط تأییدشده و مجوز انسان انجام شود.
- گزارش نهایی با داده واقعی بخواند.
